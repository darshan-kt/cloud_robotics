# 06 — Video Streaming (GStreamer + WebRTC)

> **Status: complete.** Video streams from the robot's camera to a real Chrome browser over WebRTC, end to end, verified live: `videoWidth`/`videoHeight` report the real 640×480 frame size, `currentTime` advances in real time, `readyState` reaches `HAVE_ENOUGH_DATA`, and the pipeline's own RTP-packet counter climbs continuously against the connected peer. Getting there took five debugging passes across two sessions - a genuinely long story, and one worth reading in full below, because the actual root cause (an unset `stream-format` field) was not any of the four hypotheses chased first (a native-library segfault, a `profile-level-id` byte mismatch, an RTP payload-type mismatch, and a `webrtcbin` object-graph binding gap) even though each of those *was* real and worth fixing along the way. See "Fifth debugging pass" below for the actual fix, and the rest of this doc for the complete history.

## What this step is

The camera path from the master spec: `Camera → ROS2 → GStreamer → WebRTC → Browser`. `RealROSAdapter` subscribes to `/camera/image_raw` and converts each `sensor_msgs/Image` into the agent's own `CameraFrame` domain type. A new `VideoStreamer` owns a GStreamer pipeline that takes those frames, encodes them as H264, and transports them over WebRTC via GStreamer's own `webrtcbin` element — never MJPEG, never RTSP, per the spec's explicit prohibitions. `RealROSAdapter`/`VideoStreamer` don't know or care who publishes `/camera/image_raw` — see the next section for what actually does, and why that changed.

## The camera-source pivot: a real webcam, not Gazebo's simulated camera

This milestone originally wired up Gazebo's `waffle_pi` simulated camera sensor (see "Bug 1" below for that whole saga: it needed a virtual display, Xvfb, just to render at all). That was later reverted in favor of a real, locally-attached webcam: **`webcam_driver.py`**, a small standalone ROS2 node using OpenCV/V4L2, publishes real camera frames onto the exact same `/camera/image_raw` topic Gazebo's camera used to. Gazebo keeps driving physics/`cmd_vel`/`odom` exactly as in Milestone 5 — only the camera's *source* changed.

Two reasons, one of them found the hard way mid-session:

1. **The obvious one**: a real webcam is a more honest signal than a simulated camera pointed at a Gazebo world — the point of Milestone 6 is proving the video *pipeline*, and a real image source removes a whole axis of "is this actually representative" doubt.
2. **The one found by hitting it**: Gazebo (headless gzserver) + ROS2 + a live GStreamer/x264 encode pipeline + a Chrome instance under Playwright automation, all at once, is genuinely heavy — heavy enough that it **crash-looped this project's own 7.6GiB dev machine** during this debugging session (confirmed via `last -x`, which showed several sub-15-minute boots and one session explicitly logged as ending in a `crash`, each overlapping exactly with a heavy build+Gazebo+Chrome cycle). Dropping Gazebo's camera sensor (and the Xvfb/display machinery that existed only to make it render) cut the robot container's steady-state footprint by roughly 80% — from ~3GiB RAM / ~354% CPU down to ~620MiB RAM / ~150% CPU, measured with `docker stats` before and after on the same machine. That was enough headroom to make a real-browser test survivable again. See "A note on system stability" further down for the full story and the other mitigations added alongside this.

`webcam_driver.py` opens `CAMERA_DEVICE` (default `/dev/video0`) via OpenCV/V4L2 and publishes at `CAMERA_FPS` (default 15). It is **not** passed through to the container by default — `docker compose up` must keep working on a machine with no webcam attached at all, which this project's own dev environment currently is (no `/dev/video*` present). Real hardware passthrough is an opt-in override, `docker-compose.camera.yml` (see "Running it yourself"). For dev/CI machines with literally no camera, `CAMERA_TEST_PATTERN_FALLBACK=true` makes the node publish a clearly-labelled synthetic animated pattern instead of failing silently — **off by default**, deliberately: a real deployment with no camera should fail loudly (repeated warnings, zero frames), not quietly substitute fake video. This is the same "clearly-labelled, never-hidden stand-in" convention `dev_signalling_server.py` itself once followed (see below - it's since been deleted, its job done for real by [Milestone 8](08-webrtc-signalling.md)) and `tests/fake_video_streamer.py` still does.

## Why it's needed

### Why `webrtcbin`, not `aiortc`, does the transport

The obvious-looking alternative — GStreamer encodes, a pure-Python library like `aiortc` handles WebRTC transport — was considered and rejected. `aiortc`'s public API encodes frames itself (via PyAV/FFmpeg) inside its own RTP sender loop; there's no clean way to hand it pre-encoded H264 from `x264enc` without monkey-patching its internals. That would mean `aiortc`, not GStreamer, is doing the actual encoding — which doesn't satisfy "GStreamer encodes H264" as written. Instead, one unified pipeline does capture-side conversion, encoding, *and* transport:

```
appsrc → videoconvert → x264enc → rtph264pay → webrtcbin
```

This matches the spec's architecture diagram literally (GStreamer feeds WebRTC directly) instead of bridging two frameworks.

### Why the pipeline is built lazily, on the first frame

Building the `appsrc` caps (`width`, `height`, `format`) requires knowing the actual camera resolution and pixel encoding. Rather than hardcoding `waffle_pi`'s current 640×480/`rgb8` and hoping it never changes, `VideoStreamer` waits for the first real `CameraFrame` and builds the pipeline from whatever it reports.

### Why every pipeline interaction runs on one GLib thread

GStreamer's C-level event loop can't share a thread with Python's `asyncio` loop, so `VideoStreamer` runs its own `GLib.MainLoop` on a background thread — the same "own thread, dispatch via stored state" shape as `MockROSAdapter` and `RealROSAdapter`. But there's a second reason this matters here specifically, discovered the hard way (see below): concurrent access to `webrtcbin` and the GStreamer objects it hands back — from a ROS2 camera-callback thread pushing frames while an HTTP thread negotiates SDP — reproducibly corrupts memory on this stack. `_run_on_main_loop()` marshals every single touch of the pipeline, `webrtcbin`, or anything derived from it onto that one thread, via `GLib.idle_add()`.

### Why the dev signalling server was explicitly temporary (and is now gone)

WebRTC needs *some* channel to exchange an SDP offer/answer before video can flow. While the real one — MQTT-mediated, through the backend — didn't exist yet, `dev_signalling_server.py` stood in for it: a small, clearly-labeled, throwaway `ThreadingHTTPServer` (same pattern as `health_server.py`): `GET /` served a single-file HTML test page, `POST /offer` handed the offer to `VideoStreamer.handle_offer()` and returned the answer. Non-trickle ICE (wait for full candidate gathering before answering) avoided needing a second channel for ongoing candidate exchange just for temporary dev tooling - a design choice that carried over unchanged into the real signalling path. **[Milestone 8](08-webrtc-signalling.md) deleted this file entirely**, exactly as its own docstring always said it would - `handle_offer()` itself is unchanged; only what calls it is.

## What actually broke, and how it got fixed

This is the longest debugging story in the project so far, spanning multiple sessions — worth documenting honestly and in some detail, the same standard set in Milestones 3 and 5.

**Bug 1 — Gazebo's camera needs a real display.** `/camera/image_raw` had zero publishers despite the model SDF correctly referencing `libgazebo_ros_camera.so`. Gazebo's own log (`~/.gazebo/server-*/default.log`) showed the real cause: `Can't open display` → the camera sensor's render engine can't initialize and silently disables itself, while physics/odometry keep working fine (which is why this went unnoticed until this milestone). **Fix at the time**: installed `xvfb`, added `DISPLAY=:99`, and started `Xvfb :99 -screen 0 1280x1024x24 &` in `entrypoint.sh` before the simulation launches. Confirmed working: ~714 camera frames in 24 seconds, matching Gazebo's 30fps `update_rate`.
>
> **Superseded**: this whole fix was later reverted — see "The camera-source pivot" above. Kept here because it's real, useful history (the root-causing method — reading Gazebo's own log rather than guessing — generalizes), not because Xvfb is still part of this project.

**Bug 2 — `gi.require_version()` order.** `Gst.Structure.get_value()` on a promise reply was returning a generic, useless `GBoxed` wrapper instead of a proper `WebRTCSessionDescription` (`.sdp` attribute access raised `AttributeError`). Root cause: `GstWebRTC` was `require_version`'d before `GstSdp`. `WebRTCSessionDescription` embeds a `GstSDPMessage*` internally, and PyGObject needs `GstSdp`'s typelib resolved first to correctly unbox the nested type. **Fix**: reorder to `Gst` → `GstSdp` → `GstWebRTC`.

**Bug 3 — the real one: a deterministic native segfault in `libgstsdp`.** With bug 2 fixed, SDP parsing and `set-remote-description`/`create-answer` all reliably succeeded — but the process then crashed with `error 4` (invalid memory access) inside `libgstsdp-1.0.so`, every time, only when negotiating against a **real** cross-process peer (`aiortc`, standing in for a browser since no browser-automation tooling is available here). Synthetic, same-process SDP never triggered it, which is what made this so hard to pin down initially.

Chasing this took a systematic elimination process:
- Isolated whether ROS2/rclpy/MQTT/asyncio were factors, by building a standalone process with none of them, feeding it synthetic frames directly through the real `VideoStreamer` — **still crashed**. Ruled out the whole ROS2/asyncio stack.
- Suspected thread concurrency (a frame push racing SDP negotiation) and rewrote every pipeline/`webrtcbin` interaction to run through `GLib.idle_add()` on the single GLib main-loop thread — **still crashed**, even with a variant that pushed zero concurrent frames during negotiation. Ruled out concurrent frame-pushing.
- The decisive step was reading **kernel segfault logs** directly (`journalctl -k | grep segfault`) instead of only trusting Python-level tracebacks. Every crash showed the identical relative offset inside `libgstsdp`, regardless of which mitigation was active — proof this was one deterministic bug, not a timing-dependent race.
- Added targeted logging immediately before and after every single operation touching `libgstsdp` or values derived from it, to find the *exact* line. This narrowed it down precisely: the crash happened on `answer.sdp` — an ordinary-looking attribute access on the `WebRTCSessionDescription` object returned by `create-answer`'s promise reply — not inside `.as_text()` as first suspected, and not inside `get_value()` itself (which reported the correct Python type just fine).

**Root cause**: `answer_promise.get_reply().get_value("answer")`, chained in one expression with no name bound to the reply, lets CPython drop the reply `Gst.Structure`'s refcount to zero as soon as the chain finishes. The boxed `WebRTCSessionDescription` value extracted from it **borrows** its internal `GstSDPMessage*` rather than duplicating it — so once the temporary structure is garbage collected, that pointer dangles. The very next access to it (`.sdp`) dereferences invalid memory. The same hazard applied a second time: the extracted `answer` object was reused later for `set-local-description`, by which point its backing `reply` had already gone out of scope in the original code.

**Fix**: bind `reply = answer_promise.get_reply()` to a real variable, and keep it alive (via a `keep_alive` list at `handle_offer`'s own scope) for as long as anything derived from it — the `answer` object — is still in use, all the way through `set-local-description`. The same "read the property and use it in the very same callback, never let the boxed value cross a thread or outlive its source" rule was applied to the `local-description` read at the end of negotiation too.

Verified repeatedly, including after intentionally reverting an unrelated attempted fix (extra RTP `fmtp` caps, see "First debugging pass" below) that itself briefly reintroduced pipeline errors: with the `keep_alive` fix in place, the complete offer → `set-remote-description` → `create-answer` → answer extraction → `set-local-description` → ICE-gathering chain now runs against the real `aiortc` client with **zero crashes**, every time.

One more lesson from this saga: a mid-debugging attempt to add *more* diagnostic visibility — connecting `notify::ice-gathering-state`/`on-ice-candidate` signal handlers directly on `webrtcbin` — briefly reintroduced a crash of its own. GObject `notify::` signals fire on whatever thread actually changed the property (GStreamer's internal ICE/`libnice` machinery, not the GLib main-loop thread this file marshals everything onto), so an unmarshalled handler is exactly the kind of foreign-thread access this file's whole design exists to avoid. Removed once identified.

## First debugging pass: the profile-level-id byte-mismatch theory

> This section is the **original** diagnosis from the first debugging session, using `aiortc` as the only available peer (no browser-automation tooling existed in that session's environment). Kept as real history — the root-causing method is still worth reading — but see "Second debugging pass" below for what a real browser and further isolation actually showed: this theory was plausible and precisely measured, but turned out not to be the operative blocker. `webrtcbin`'s answer-generation never got far enough to evaluate it at all - see below.

With the segfault fixed, ICE connectivity itself works — a real `aiortc` client's `iceConnectionState` reaches `completed`. But zero video frames arrive. This was tracked down precisely, not left as a guess:

Inspecting the SDP answer showed `webrtcbin`'s `create-answer` responding with `a=inactive`, echoing back `VP8` even though the offering peer clearly proposed two H264 payload types alongside VP8. A read-only diagnostic (querying `webrtcbin.get-transceivers()` and the sink pad's actual negotiated caps via `pad.get_current_caps()`) confirmed our GStreamer-side caps negotiation itself was fine — there was exactly one transceiver, correctly carrying H264 caps with a real `profile-level-id`. So the pipeline wasn't failing to produce H264; `webrtcbin`'s *answer-generation* logic was failing to recognize it as a match for the offer.

Comparing values made the mechanism exact: the offer's two H264 entries declared `profile-level-id=42001f` and `profile-level-id=42e01f` (RFC 6184: profile_idc / constraint-flags / level_idc, as three hex byte-pairs). Our pipeline's actual negotiated caps showed `profile-level-id=42c014` — the level byte (`14` = Level 2.0) didn't match either offer because `x264enc` was auto-selecting a level purely from the 64×64 synthetic test frame size. Forcing the level explicitly (`video/x-h264,profile=baseline,level=(string)3.1` right after `x264enc`, a real negotiation point the encoder honors) fixed that part — the caps then showed `profile-level-id=42c01f`, matching the offer's level nibble (`...1f`) exactly. But the middle byte (constraint flags) still didn't match: GStreamer's `profile=baseline` setting always produces `0xc0`, while the offer only proposes `0x00` or `0xe0`. `webrtcbin` appears to require a literal byte-for-byte match on this field rather than RFC 6184's actual profile-compatibility semantics (where `0xc0` is arguably compatible with both), so negotiation still fails.

An earlier attempt to just force the *exact* value downstream — adding `packetization-mode`/`profile-level-id` fields directly to the RTP capsfilter between `rtph264pay` and `webrtcbin` — was tried and reverted: a capsfilter can only narrow among values an upstream element actually offers, and `rtph264pay`'s real output caps don't include arbitrary caller-chosen `profile-level-id` values as an option, so this broke pipeline-internal negotiation entirely (`streaming stopped, reason not-negotiated`) before WebRTC signalling was even reached.

**A second fix attempt, and why it was reverted too.** The natural next step: explicitly tell `webrtcbin` what to advertise, via its `add-transceiver` action signal and a transceiver's `codec-preferences` property, instead of relying on it to infer the right SDP from the pad's raw negotiated caps. This is the documented, intended mechanism for exactly this kind of control, so it was worth building properly:

1. Stopped linking the payloader to `webrtcbin` via `Gst.parse_launch`'s static `!` syntax (which auto-creates a transceiver from the pad's raw caps - the thing that isn't working). Built `webrtcbin` as a separate element instead.
2. Called `webrtcbin.emit("add-transceiver", SENDONLY, codec_caps)` with `codec_caps` explicitly declaring `profile-level-id=42e01f` - a value confirmed to be one of the two the offer actually proposes - *before* linking any pad.
3. Requested a sink pad and linked the payloader to it by hand.

Two real GStreamer/PyGObject rough edges showed up along the way, both confirmed empirically rather than assumed:

- `webrtcbin.emit("get-transceivers")` returns a `GLib.Array` whose element type isn't marshaled correctly by this PyGObject/GIR combination - indexing it (`transceivers.data[0]`, or even the `Array` itself via `[0]`) raises `UnicodeDecodeError`, because the generic array wrapper tries to interpret the raw pointer array as UTF-8 text. `webrtcbin.get_transceivers()` as a direct bound method also doesn't exist on this binding. There's no way found in this session to enumerate *existing* transceivers from Python on this stack - only to create new ones (`add-transceiver`, which returns a single object directly and isn't affected).
- Requesting a sink pad via the wildcard template (`get_request_pad("sink_%u")`) does **not** bind to the transceiver just created - confirmed by checking `get-transceivers().len` before and after, which went `1 → 2`. It silently creates a second, separate, unconfigured transceiver, leaving the one with our codec preferences unlinked and unused. Requesting the concrete pad name for its mline index instead (`get_request_pad("sink_0")`) does bind to the existing transceiver by count - but the resulting SDP answer this produced was a step backward, not forward: a structurally rejected m-line (`m=video 0 ...`) missing `a=setup` entirely, which `aiortc` itself refused to even apply (`ValueError: DTLS setup attribute must be 'active' or 'passive' for an answer`). Something about this exact combination of manual pad linking confuses `webrtcbin`'s own answer-generation further, in a way not resolved in this session.

Given the second attempt produced a worse, structurally invalid result rather than a better one, it was reverted. The codebase is back to the simpler, stable version (static `!` linking, plus the genuine `level=3.1` fix, which is kept as-is since it demonstrably corrected part of the mismatch and caused no regressions).

Closing this gap fully needs one of: (a) figuring out the correct way to bind a pre-configured transceiver to a linked pad on this specific `webrtcbin` version - the `sink_0` approach was close but broke something else; (b) confirming whether this is version-specific to `gstreamer1.0-plugins-bad` 1.20.x (Ubuntu 22.04's version) and doesn't reproduce on newer GStreamer; or (c) testing against a **real browser** instead of `aiortc` - chosen here only as a scriptable stand-in for a browser since no browser-automation tooling exists in this environment, but a real browser's negotiation logic might be more tolerant of the original profile-level-id mismatch, making this whole transceiver detour unnecessary. That's the highest-value next check, and one this environment genuinely cannot do itself - worth trying directly against the dev signalling page (see below) before investing more time on the GStreamer side.

This was recorded as a precisely-diagnosed open item, including a documented dead end, rather than smoothed over - consistent with this project's documentation standard. It's also where the first debugging session ended.

## Second debugging pass: verified against a real browser, and a real fix

This session picked the milestone back up with one new capability the first session explicitly didn't have: a real Chrome browser plus Playwright, actually available in this environment (the first session's docs repeatedly noted "no browser-automation tooling is available here" - that turned out to be an assumption worth re-checking, not a permanent fact about the environment).

**First result: real Chrome hits the identical wall.** Driving the dev signalling page with headless Chrome (`channel="chrome"` via Playwright, not the previous session's `aiortc` stand-in) reproduced the exact same symptom byte-for-byte: `iceConnectionState` reaches `connected`, the answer comes back `a=inactive` with `VP8` echoed at payload type 96, zero video frames. This directly answers the open question option (c) from the first pass ("a real browser's negotiation logic might be more tolerant") — **no, it isn't**, at least not for whatever `webrtcbin` was actually doing here. That ruled out one whole branch of the earlier investigation and pointed at something more fundamental than profile-level-id tolerance.

**The actual root cause, found by inspecting the real offer text directly:** Chrome's real offer bundles every codec option into a *single* `m=video` line with many alternative payload types - `VP8` at the conventional low number **96**, `H264` at scattered dynamic numbers like **103, 107, 109, 117, ...** (see the fmtp lines captured directly from a real Chrome offer, reproduced in `tests/test_sdp_utils.py`). This project's pipeline had `rtph264pay ... pt=96` hardcoded - meaning it was calling its own H264 stream "payload type 96", the exact same number Chrome's offer uses for **VP8**. `webrtcbin`'s `create-answer` never got as far as comparing `profile-level-id` bytes at all: it couldn't find *any* offered entry at payload type 96 whose encoding-name was H264, so it fell back to echoing the offer's own PT-96 entry (VP8) as an inert placeholder, marked `a=inactive`, regardless of what our actual pad caps said. This is confirmed directly and cheaply (see "A note on system stability" for why "cheaply" mattered here): a standalone script that builds a real `VideoStreamer`, pushes one synthetic frame, and calls `create-answer` against a saved real-Chrome offer reproduces the inactive/VP8 answer with zero Gazebo, ROS2, or browser involved — the fastest possible iteration loop for this class of bug.

**The fix, in two parts, both in `robot_agent/sdp_utils.py`** (deliberately dependency-free — no `gi`/GStreamer import — so this logic is actually unit-tested, unlike `video_streamer.py` itself; see `tests/test_sdp_utils.py`, which exercises it against real captured Chrome SDP fragments):

1. **`choose_offer_h264_payload_type(offer_sdp)`** — reads the offer's own H264 payload-type numbers (RFC 3264 requires the answerer to select from the offer's own numbering, never invent one) and picks the best match: prefers `packetization-mode=1` (what `rtph264pay` produces) and the `42...` (baseline) profile family, since that's the family `x264enc`'s zerolatency baseline output actually belongs to.
2. **`rewrite_answer_for_real_codec_match(answer_sdp, pt, profile_level_id)`** — `create-answer`'s own output isn't trustworthy here (confirmed above), so `handle_offer()` no longer hands it to `set-local-description` untouched. It hand-edits the m-line/`rtpmap`/`rtcp-fb` to the chosen payload-type number, flips `a=inactive` → `a=sendonly`, and adds an `fmtp` line carrying **our own actual** `profile-level-id` (read straight off the payloader's real negotiated caps, not guessed or copied from the offer — real H264 decoders read the profile from the bitstream's SPS regardless of what `fmtp` claims, so this is honest rather than a workaround stacked on a workaround).

`video_streamer.py`'s `_retarget_payload_type()` also changes `rtph264pay`'s own `pt` property (and the RTP capsfilter's `payload` field) to the chosen number *before* negotiating, and forces one cached frame through the pipeline immediately after — a plain property change alone doesn't reach `webrtcbin`'s sink pad, since GStreamer only pushes a new CAPS event ahead of the next buffer that actually flows, and `push_frame()` stops pushing during negotiation (see the module docstring for why).

**Confirmed working, against real Chrome's actual SDP** (this is the part that's genuinely new and fixed - previously the answer was *always* `a=inactive`/VP8, unconditionally):

```
>> m=video 9 UDP/TLS/RTP/SAVPF 103
>> a=rtpmap:103 H264/90000
>> a=sendonly
>> a=fmtp:103 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42c01f
```

`set-local-description` **accepts** this hand-edited description and reconfigures `webrtcbin`'s own internal state to match (`local-description` afterward genuinely reflects `sendonly`/103/H264, not just the text we handed it) - confirmed directly, not assumed.

**What's still open after this pass:** even with negotiation now correctly reaching an active H264 answer, the real Chrome test still shows zero decoded frames (`<video>` element's `videoWidth`/`videoHeight` stay 0). A follow-up, Gazebo-free check pushed 60 real (non-identical) frames through the actual pipeline *after* a completed negotiation and watched the payloader's output pad with a raw buffer probe: zero RTP buffers observed there, even though the same pad's derived `profile-level-id` (used in the fmtp line above) proves at least one real encoded buffer *did* flow through it earlier, during setup. At the time, the leading hypothesis was that `webrtcbin` gates actual RTP transmission on DTLS/SRTP actually being established, and that the standalone test (no live peer) simply couldn't exercise that. See "Third debugging pass" below for whether that held up.

## Third debugging pass: a real RTP-packet counter, watched live against a real connected browser

The open question from the second pass had a genuine gap in it: the buffer-level probe that found "zero RTP buffers post-negotiation" was never run *at the same time* as an actual live, ICE-connected Chrome session - only offline, against a replayed saved offer with no real peer on the other end. That's a real experimental gap, not just a loose end - it's entirely possible `webrtcbin` correctly withholds media until a transport is actually secured, in which case the offline test's "zero buffers" result would say nothing about the real Chrome case. Closing that gap needed the full Gazebo+Chrome combination running at once, with instrumentation - so it also needed the resource discipline from "A note on system stability" below to attempt safely.

**Real, permanent instrumentation, not just an ad hoc probe.** `VideoStreamer` now has a buffer probe on the payloader's src pad built into `_build_pipeline()` itself, counting every RTP packet actually emitted and reading its real payload-type byte off the wire (`rtp_packets_sent`, `last_rtp_payload_type`) - exposed through `RobotCloudAgent.get_metrics()` and therefore `/metrics`. This is useful going forward regardless of this specific bug: it's the honest way to answer "is media actually flowing", which turned out to be a different question from "did signalling succeed" or "are camera frames arriving" (see `docs/06-video-streaming.md`'s own earlier confusion between those). `tests/fake_video_streamer.py` reports it as `0` - honestly, since it has no real pipeline to count anything on.

**First, a Gazebo-free sanity check of the counter itself** (same lightweight pattern as before) found something sharper than the second pass's probe had: `rtp_packets_sent` reaches exactly **1** during pipeline setup (before any negotiation is even attempted) and then never increases, no matter how many more frames are pushed - and a further probe on *every* stage of the pipeline (`appsrc`'s own src pad, `x264enc`'s src pad, the payloader's src pad) showed **zero** buffers at any of them, while `appsrc`'s internal queue (`current-level-bytes`) grew to over 90× its configured `max-bytes`, one whole frame's worth of accumulation per `push_frame()` call. `appsrc` accepts every `push-buffer()` call (returns `GST_FLOW_OK`, which is why `frames_pushed` and `camera_frames_received` both climb normally) but was not observed forwarding any of them into the rest of the pipeline in this offline configuration.

**Then, the real test**: the full stack (real `robot`/`mosquitto` containers, `webcam_driver.py`'s synthetic fallback since this dev machine has no camera) driven by an actual Chrome browser via Playwright, polling `/metrics` once a second for the whole session. `iceConnectionState` reached `connected` and held there for the full 20-second observation window, while `camera_frames_received` climbed normally throughout (186 → 374) - proving frames were still arriving from the camera source the entire time. `rtp_packets_sent`, watched over that same live, genuinely-connected window: **stuck at 1, the entire time.**

This is conclusive, not another hypothesis: **the "gated on a real ICE connection" theory from the second pass is wrong.** ICE was genuinely connected, for 20 real seconds, and the pipeline still emitted exactly one RTP packet. Something about how this project's `set-local-description` override (the hand-rewritten SDP from the second pass) leaves `webrtcbin`'s *internal* transceiver/RTP-session state - separate from what `local-description` reports as text, which does correctly say `sendonly` - never actually transitions into continuously sending. The negotiation-level fix from the second pass is real and necessary (a raw text mismatch would have blocked things regardless), but it is not sufficient on its own, and this is a different, deeper problem than SDP text correctness.

## Fourth debugging pass: found exactly which internal state is broken

The third pass established *that* `webrtcbin`'s internal state diverges from what its own `local-description` text reports. This pass found *which* internal state, by reading the actual `GstWebRTCRTPTransceiver` object rather than only the SDP text it produces.

**A cleaner way to reach it, found along the way**: the first pass's docs noted `webrtcbin.emit("get-transceivers")` (plural) returns a `GLib.Array` that this PyGObject/GIR combination marshals incorrectly (`UnicodeDecodeError`). `gst-inspect-1.0 webrtcbin` shows a second, singular action signal that sidesteps this entirely: **`get-transceiver`** (`gint index -> GstWebRTCRTPTransceiver*`), returning one real object directly, no array marshaling involved. With only one transceiver in this pipeline, `webrtcbin.emit("get-transceiver", 0)` is all that's needed.

**What it showed, immediately after a full `handle_offer()` negotiation** (the real production code path, including the second pass's answer rewrite):

```
direction=SENDRECV current-direction=SENDRECV
mid=None
mlineindex=4294967295          # 0xFFFFFFFF - the unsigned "unset" sentinel, not a real value
sender.transport=None
```

Three findings, and the third is the actual smoking gun:

- **`direction`/`current-direction` are `SENDRECV`**, not blocking anything - direction was never the problem, despite it being the most visible/obvious property to suspect.
- **`mid` is `None`** and **`mlineindex` is the raw unsigned "unset" sentinel value**, not `0` - even though the SDP text we hand-rewrote and successfully applied via `set-local-description` clearly contains `a=mid:0`. The transceiver object itself was never actually bound to that mid.
- **`sender.transport` is `None`.** This is the direct, mechanistic explanation for why sending never continues: a `GstWebRTCRTPSender` with no transport object has nowhere to write RTP packets *to*, at the C level, regardless of whether ICE is connected somewhere else in the bundle. It isn't a policy/direction gate - it's a literal missing pointer.

**Ruled out timing as the cause, cheaply**: retargeting the RTP payload type immediately on pipeline build (not just right before answering), then giving it 10 real frames and 2 full seconds to settle - all *before* any offer even exists - made no difference. `create-answer` still produced the same inactive/mismatched result requiring the rewrite, and the transceiver's `mid`/`mlineindex`/`sender.transport` were identically unset afterward. This wasn't a caps-propagation race that more patience would fix.

**Why the text-rewrite approach structurally cannot reach this**: `mid`, `mlineindex`, and `sender.transport` are assigned as a side effect of `webrtcbin`'s own *internal* SDP-application logic succeeding on its own terms during `create-answer`/`set-local-description` - not derived by re-parsing arbitrary SDP text handed to `set-local-description` afterward. Our rewrite changes what the pipeline *reports*, and it's real (the second pass's fix is genuinely necessary - Chrome would reject an SDP with the wrong payload-type numbering outright), but it can't retroactively populate object graph state that only gets set when `webrtcbin`'s native negotiation path actually succeeds. That's the real reason this milestone isn't closed by the second pass's fix alone.

**What this rules in as the next step, precisely**: fixing this needs `create-answer` (or an equivalent native path, like `add-transceiver`) to succeed *on its own*, not a text patch applied after it fails. The first debugging pass tried exactly this (`add-transceiver` + `codec-preferences`) and reverted it - but for reasons now understood much more precisely: it hit a *pad-linking* problem (`get_request_pad("sink_%u")` silently creating a second, unrelated transceiver instead of binding to the one just configured), not a fundamental impossibility. With `get-transceiver`'s clean, singular lookup (found this pass) to verify binding correctness immediately, and now knowing exactly which three properties constitute "actually bound" (`mid`, `mlineindex`, `sender.transport` all non-null/valid), a second, better-informed attempt at that same approach is the most direct path left. See "Fifth debugging pass" for what that attempt actually found.

## Fifth debugging pass: the actual fix

This pass set out to retry `add-transceiver` as the fourth pass recommended. It ended up finding something else entirely - and this is the pass that actually closes the milestone, so it's worth reading in full.

**`add-transceiver` + `codec-preferences`, retried properly, made things worse again.** Re-attempted with `get-transceiver`'s clean lookup to verify binding at every step: `add-transceiver` itself worked fine (a transceiver appeared, correctly `SENDONLY`, correctly bound at index 0). But requesting the concrete `sink_0` pad afterward - confirmed by the first pass to bind-by-count, and re-confirmed here on *two* GStreamer versions (1.20.3 and 1.24.2 both) - reliably creates a **second, separate transceiver** instead (transceiver count goes `1 → 2` every time), and `create-answer` then uses the *wrong* one, producing a result even worse than plain `a=inactive`: a fully rejected m-line (`m=video 0 ...`, `a=recvonly`). This wasn't a version-specific bug either - confirmed identical on both versions. `add-transceiver` was a dead end, a second time, now on stronger evidence.

**The pivot: is `create-answer`'s failure about codec matching at all?** Testing directly on GStreamer 1.24.2 (installed fresh, alongside the project's shipped 1.20.3, specifically to separate "is this a GStreamer version bug" from "is this a bug in our own pipeline or code") with the *simplest possible* pipeline - no retargeting, no rewriting, no `add-transceiver`, just a payload-type number that matches the offer from the moment the pipeline is built - still produced the exact same `a=inactive`/VP8 answer. Same result with `profile-level-id` genuinely, deliberately mismatched (proving the first pass's byte-mismatch theory, while real and precisely measured, was never actually the operative blocker `create-answer` was tripping on). Same result switching encoders entirely, from `x264enc` to `openh264enc` (ruling out "maybe a different encoder produces a byte-matching SPS" - it doesn't; both settle on the same `0xc0` constraint-flags convention for baseline profile, confirmed by direct inspection). **None of the four hypotheses chased across two sessions and five debugging passes - the segfault (fixed, real), the profile-level-id byte mismatch, the payload-type mismatch (real, still needed), the transceiver object-graph gap - were actually sufficient on their own to explain `create-answer`'s failure.** Something else was going on underneath all of them.

**The actual root cause, found by systematically toggling one caps field at a time**: our H264 capsfilter (`video/x-h264,profile=baseline,level=(string)3.1`) never explicitly declared `stream-format`. Adding `stream-format=(string)byte-stream` to that one caps string - and nothing else, in an otherwise maximally simple pipeline - made `create-answer` succeed **natively**, immediately, on both GStreamer 1.20.3 (this project's shipped version) and 1.24.2: `a=sendonly`, correctly-numbered `a=rtpmap`, and - the real proof, checked directly via `get-transceiver` - `mid`, `mlineindex`, and `sender.transport` all populated correctly for the first time in this entire investigation. Explicitly setting `stream-format=avc` instead of `byte-stream` *also* worked - it's not about which value, it's about the field being **explicit rather than left as an unconstrained wildcard**. Left unset (this pipeline's state through four debugging passes), something about the resulting caps ambiguity makes `create-answer`'s internal matching fail to bind a transceiver at all, silently, with no error - not a payload-type or profile-level-id problem, an entirely different and much more basic caps-negotiation gap that happened to *look* like those other things from the outside (an inert, unbound `a=inactive` answer) at every point this was tested from Python.

**One more real finding along the way, needed to make the fix work in this project's actual architecture**: a caps property change on an *already-negotiated* pad - even with `stream-format` now fixed - does not reliably reach `webrtcbin`'s internal negotiation state the same way a *fresh* pad link does. Confirmed directly: retargeting the payload type via property change after pipeline warm-up (exactly what this project's pipeline did going into this pass - build once, retarget later when an offer arrives) still failed, while linking a **freshly-requested** webrtcbin pad, with correct caps from the very first link, succeeded every time. This meant the fix needed a structural change, not just an added caps field: `VideoStreamer`'s encode chain (`appsrc` .. `rtph264pay`) now builds and starts immediately as before, camera frames flowing and getting encoded from the start - but terminates in a throwaway `fakesink` instead of `webrtcbin`. `webrtcbin` itself is built as a separate element, added to the pipeline but left unlinked. Only when the first offer actually arrives - `_ensure_webrtcbin_linked()`, called from `handle_offer()` - does the code retarget the payload type, detach from the `fakesink`, request a **fresh** `sink_%u` pad on `webrtcbin`, and link the encode chain into it for the first time. `webrtcbin` never sees a caps mismatch or ambiguity at any point in its life.

With this in place, the second pass's answer-rewrite (`rewrite_answer_for_real_codec_match`) is no longer needed on the primary path - `create-answer`'s own native output is correct - but it's kept in `robot_agent/sdp_utils.py` as a defensive fallback (still unit-tested; its own no-op branch makes it free when create-answer already succeeded, which is now the normal case).

**Verified, completely, end to end**: driving the real dev signalling page with an actual Chrome browser (via Playwright) against the real, full container stack (Gazebo + ROS2 + this pipeline): `iceConnectionState` reaches `connected`, the `<video>` element reports `videoWidth: 640, videoHeight: 480`, `readyState: 4` (`HAVE_ENOUGH_DATA`), `paused: false`, and `currentTime` **advances in real time** (`0.839s → 3.95s` over a real 3-second wait - genuinely decoding, not a single stale frame). `/metrics`' `rtp_packets_sent` climbed continuously throughout (`284` and rising) against the live, connected peer - not the "exactly 1, forever" result every earlier pass measured. This is the first point in this milestone's entire history that real video has reached a real browser.

## A note on system stability

This debugging pass surfaced a second, unrelated but important problem: running Gazebo (headless `gzserver`) + ROS2 + a live GStreamer/x264 pipeline + a real Chrome instance under Playwright automation, all at once, is heavy enough that it **crash-looped this project's own dev machine** (7.6GiB RAM) mid-session. `last -x` showed the evidence directly: several sub-15-minute boot cycles and one session explicitly logged as ending in a `crash`, each overlapping exactly with a heavy build+Gazebo+Chrome cycle, and `free -h` showed swap climbing steadily under load (not a clean OOM-kill — this reads as swap-thrashing making the whole desktop unresponsive, not just this project's containers).

Mitigations, all now in place:

- **The camera-source pivot itself helped enormously** (see above) - dropping Gazebo's simulated camera and the Xvfb it needed cut the robot container's steady-state footprint from ~3GiB RAM / ~354% CPU to ~620MiB RAM / ~150% CPU, measured with `docker stats` before and after on the same machine, same workload otherwise.
- **`docker-compose.yml`** now caps the `robot` service at `deploy.resources.limits: cpus: "4.0", memory: 3.5G` - a deliberately conservative safety net (raise it if your host has more headroom), so a runaway container gets cgroup-limited (and, worst case, the kernel OOM-killer targets something *inside* that cgroup) instead of taking down the whole host.
- **A lightweight, Gazebo-free testing methodology** for iterating on negotiation logic specifically: a throwaway container (`docker run --rm --memory=1.5g --cpus=2 --entrypoint sleep ...`) with `video_streamer.py` copied in, driving `VideoStreamer` directly against a saved real-Chrome offer - no ROS2, no Gazebo, no browser. This is how the PT-mismatch root cause and the SDP-rewrite fix above were found and verified cheaply; it's a good pattern for continuing this specific investigation without repeating the crash.

## What it does

- **`robot_agent/models.py`** — `CameraFrame(data, width, height, encoding)`. `encoding` is the ROS2 `sensor_msgs/Image` encoding string (`rgb8`, `bgr8`, …) — `VideoStreamer` needs it, with width/height, to build correct GStreamer caps.
- **`robot_agent/interfaces.py`** — `ROSAdapter.subscribe_camera()`'s callback type evolved from Milestone 4's placeholder `Callable[[bytes], None]` to `Callable[[CameraFrame], None]`, now that there's a real consumer.
- **`robot_agent/video_streamer.py`** — `VideoStreamer`: owns the GLib main loop thread, builds the encode chain lazily on the first frame (terminating in a throwaway `fakesink` - see "Fifth debugging pass"), `push_frame()`, `start()`/`stop()`, and `handle_offer(sdp) -> sdp`. `_ensure_webrtcbin_linked()` links the encode chain into `webrtcbin` for the first time once an offer reveals the real payload-type number to use - the actual fix, see "Fifth debugging pass". Counts real RTP packets emitted (`rtp_packets_sent`, `last_rtp_payload_type`) via a buffer probe on the payloader's src pad, gated on `webrtcbin` actually being linked so it only counts packets genuinely headed at a peer.
- **`robot_agent/sdp_utils.py`** — `choose_offer_h264_payload_type` (still needed - RFC 3264 requires answering with the offer's own payload-type numbering) and `rewrite_answer_for_real_codec_match` (no longer needed on the primary path now that `create-answer` succeeds natively, but kept as a tested, free-when-unneeded defensive fallback). Deliberately dependency-free so it's unit-tested (`tests/test_sdp_utils.py`) despite `video_streamer.py` itself not being (GStreamer/PyGObject aren't pip-installable in the lightweight test venv).
- **`ros_ws/src/robot_cloud_bridge/robot_cloud_bridge/webcam_driver.py`** (new) — the real ROS2/V4L2/OpenCV webcam node described in "The camera-source pivot" above: opens `CAMERA_DEVICE`, publishes `sensor_msgs/Image` (`bgr8`) on `/camera/image_raw`, retries opening every 5s if the device is missing, and has an explicit, off-by-default synthetic test-pattern fallback (`CAMERA_TEST_PATTERN_FALLBACK`).
- **`ros_ws/src/robot_cloud_bridge/robot_cloud_bridge/real_ros_adapter.py`** — `subscribe_camera()` is a real `/camera/image_raw` subscription (`depth=1` QoS — always process the latest frame rather than build up a backlog if `VideoStreamer` falls behind), converting `sensor_msgs/Image` into `CameraFrame`. Agnostic to which node publishes that topic - doesn't know or care that it changed from Gazebo's camera to `webcam_driver.py`.
- **`ros_ws/src/robot_cloud_bridge/launch/simulation.launch.py`** — now also launches `webcam_driver` alongside `gzserver`/`robot_state_publisher`/`spawn_turtlebot3`.
- **`robot_agent/agent.py`** — constructor takes `video_streamer`; subscribes to the camera alongside odometry/battery/diagnostics; `_on_camera_frame()` forwards frames to `VideoStreamer.push_frame()`, exception-wrapped so one bad frame can't take down the ROS2 subscription; `stream_video()` reports real pipeline status (`is_pipeline_ready`, `frames_pushed`); `get_metrics()` (and therefore `/metrics`) now reports `rtp_packets_sent` too - proof media is flowing, not just that camera frames arrived or signalling succeeded.
- **`tests/fake_video_streamer.py`** — `rtp_packets_sent` always reports `0`, honestly (no real pipeline to count anything on).
- **`robot_agent/config.py` / `config/default.yaml`** — `video:` section: `bitrate_kbps`, `framerate`, `keyframe_interval`, `stun_server`. (`dev_signalling_port` removed in [Milestone 8](08-webrtc-signalling.md), along with the file it configured.)
- **`robot_agent/main.py`** — constructs and injects `VideoStreamer`. (No longer constructs `DevSignallingServer` - deleted, see [Milestone 8](08-webrtc-signalling.md); real signalling is handled directly by `RobotCloudAgent`.)
- **`docker/Dockerfile`** — GStreamer/WebRTC/PyGObject packages (`python3-gi`, the `gir1.2-gst-*` typelibs, `gstreamer1.0-plugins-good/bad/ugly` for `x264enc`, `gstreamer1.0-nice` for ICE) plus `python3-opencv`/`v4l-utils` for the webcam driver. `xvfb`/`DISPLAY`/Gazebo-camera-specific env vars removed — no longer needed, see "The camera-source pivot".
- **`docker-compose.yml`** — `CAMERA_*` env vars; `deploy.resources.limits` on the `robot` service (see "A note on system stability"). (The temporary dev signalling port/`8081` mapping is gone, see [Milestone 8](08-webrtc-signalling.md).)
- **`docker-compose.camera.yml`** (new) — optional override that actually passes a real webcam device through to the container; not applied by default.
- **`tests/test_sdp_utils.py`** (new) — unit tests for the codec-negotiation fix against real captured Chrome SDP fragments.

## Running it yourself

```bash
docker compose up -d --build
docker compose logs -f robot   # watch camera frames + pipeline build

# open in a browser:
#   http://localhost:8081/
docker compose down
```

By default this runs with **no real camera** - `webcam_driver.py` will log a clear, repeated warning and publish nothing (`CAMERA_TEST_PATTERN_FALLBACK=true` in `.env` makes it publish an obviously-synthetic animated pattern instead, off by default). To use a real, locally-attached webcam:

```bash
cp .env.example .env   # if you haven't already
docker compose -f docker-compose.yml -f docker-compose.camera.yml up -d --build
```

`CAMERA_DEVICE` (default `/dev/video0`) must exist on the **host** — check with `v4l2-ctl --list-devices` or `ls /dev/video*`.

> **Resource note**: Gazebo + ROS2 + a live GStreamer/x264 pipeline + a real browser, all running at once, is genuinely heavy - see "A note on system stability" above before running this alongside other heavy work on a small machine. `docker-compose.yml` now caps the `robot` service's memory/CPU; raise the limits if your host has more headroom.
