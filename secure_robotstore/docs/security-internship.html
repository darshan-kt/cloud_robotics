Hardening the Fleet

A threat model and a graded task programme for the cloud‑robotics teleoperation platform — a system where a browser in one country moves a physical machine in another. Everything here is scoped to the code in this repository, and every task ends in something you can prove.

22 tasks Basic → standard Sandbox: secure_robotstore Target: AWS IoT Core · ECS · RDS

00

How to use this pack

You are two computer‑science students joining a platform that lets an operator drive a real robot over the internet. Your job for the next twelve weeks is not to write features. It is to find the ways this system can be made to do something it should not — and then to close them, one at a time, with evidence.

Read Part I before you touch anything. It is six short sections and it is the difference between applying security controls you half‑understand and applying the right ones for a machine that can move.

Two environments, two purposes

Where you build

secure_robotstore/

A deliberately insecure miniature of the real stack — one device, two data types, about 1,200 lines. Same MQTT‑only device boundary, same Redis/Postgres split, same threading model. Every hole is marked INTERN TASK. You will break it and fix it repeatedly. Nothing here can hurt anyone.

What you are learning to protect

cloud-container/ + robot-container/

The real platform. It already has JWT auth with revocation, broker ACLs, rate limiting and a hash‑chained audit log — see docs/security-findings.md. You do not rebuild those. You read them after solving the same problem yourself, then audit them for what the previous passes missed.

The method — three steps, never two

Prove it. Fix it. Prove it again. Every task below opens with a command that demonstrates the weakness against a running system, and closes with the same command failing. A fix you cannot demonstrate is a fix nobody can trust, and in this system several of the most serious weaknesses are completely invisible from the user interface. If you cannot show the before, you have not earned the after.

The rule that overrides every other rule

Nothing in this programme is ever tested against a robot that can move while a person is within its reach. Simulation and the sandbox first, hardware on blocks second, hardware on the floor only with a human on a physical emergency stop. Section 09 makes this formal. Read it before your first command.

01

The system, in five boundaries

A security review that starts with a list of servers produces a list of servers. Start instead with the question that actually matters: between a student clicking “forward” and a wheel turning, how many times does one component decide to trust another? Each of those moments is a place an attacker can insert themselves, and each needs a different control.

There are four such moments in our architecture, plus the operator’s own identity. Everything in this document hangs off this picture.

Read the boundaries as questions, not as walls

Students new to security tend to picture a firewall: one wall, attacker outside, everything inside safe. That model fails here immediately, because the robot is not inside anything — it sits on a school’s Wi‑Fi, physically reachable by the same students who use it, dialling out to a cloud it cannot authenticate without help.

The useful model is the one in the picture. At every hop, the receiving side must independently answer “should I act on this?” without relying on the fact that it arrived. B3 is the boundary people forget. A message that reaches the robot over a correctly authenticated broker connection is still only proof that somebody with broker access sent it — not that the operator who appears to have sent it actually did.

02

Why this is not a web app

Most of what you have been taught about web security assumes the worst outcome is data: rows read that should not have been, records changed, an account taken over. Those are serious and they all apply here. But this system has one extra hop past the database, and that hop is made of metal.

Consequence 1

Availability is a safety property

In a web app, downtime costs money. Here, a robot that loses its command link mid‑motion must stop on its own — so the watchdog that does that is a safety control, and denial of service against the broker becomes a way to strand machines.

Consequence 2

Integrity outranks confidentiality

Reading a robot’s battery percentage is a privacy problem. Writing one is a deception problem: an operator who is shown false telemetry makes a physically wrong decision. Forged status is often worse than stolen status.

Consequence 3

The camera sees children

These robots run in schools. The video path is not a feature to secure later — it is the single most sensitive data flow in the platform, and the cheapest control is the design rule that video is never recorded.

03

The one road in: the topic contract

Every byte that moves between the cloud and a robot crosses MQTT. Not some of them — all of them. Video negotiation, commands, battery readings, LiDAR scans, heartbeats. That was a deliberate architectural decision and it is the single most valuable security property this system has, because it means there is exactly one place to enforce who may say what.

The enforcement mechanism is the topic contract: a fixed set of topic names, each with a direction. Direction is the security property. A robot publishes its own telemetry and reads its own commands; the backend publishes commands and reads telemetry. Neither is permitted to write the other’s side.

The question to ask of any new topic

When someone adds a feature that needs a new topic, the design review is two questions long. Which side authors this, and who is harmed if the other side could forge it? If the answer to the second is “an operator makes a wrong decision” or “the robot moves”, the ACL entry is not a formality — it is the control.

04

How an attacker actually gets in

Real intrusions are rarely one clever exploit. They are a chain of small, individually unremarkable steps, each one making the next possible. Understanding the chain matters more than memorising vulnerabilities, because you only have to break one link — and knowing which links you can afford to lose is what defence in depth actually means.

Here is the most plausible chain against this platform, using only weaknesses that have genuinely existed in this codebase.

05

Defence in depth, layer by layer

“Defence in depth” is repeated so often it has stopped meaning anything. Here is the version worth holding on to: each layer should stop a different class of attacker, and you should be able to say what still gets through when that layer is the only one you have. If two layers stop the same thing, you have one layer and some redundancy.

07

Who we are defending against

Threat actors are not all “hackers”. They differ in access, skill, motive and — most usefully — in which control actually stops them. Ours, roughly in order of likelihood:

Most likely · highest access

The curious student

Already on the campus network, already holds a legitimate login, has unlimited time and no malice — just curiosity and a browser devtools console. Finds things by accident. Stopped by: server‑side authorisation, because every client‑side guard is visible to them.

Likely · disruptive

The prankster

The same access, but intends to disrupt a lesson — blacking out someone’s video, driving a robot during a class, spamming commands. Stopped by: rate limits, session locks, per‑operator scoping and audit that makes it attributable.

Opportunistic

The campus network attacker

Anyone on the same Wi‑Fi: a guest, a compromised laptop, someone in the car park. Can sniff plaintext, ARP‑spoof, and reach anything bound to 0.0.0.0. Stopped by: TLS everywhere and loopback binds.

Automated · constant

The internet-wide scanner

Never targets you specifically; simply finds every exposed broker, database and metrics endpoint on the public internet within hours. Stopped by: nothing being publicly bound that does not need to be, and no default credentials anywhere.

High impact · physical

The compromised device

A robot is portable, unattended, and eventually one will be stolen or borrowed. Assume its filesystem and keys are read. Stopped by: per‑device credentials that can be revoked individually, and ACLs that scope a device to its own topics.

Rare · hardest

The insider and the supply chain

Staff with legitimate access, or a malicious dependency pulled by pip install. Neither is stopped by perimeter controls. Stopped by: least privilege, tamper‑evident audit, pinned and scanned dependencies, reviewed base images.

09

Rules of engagement

You are about to spend twelve weeks doing things that, done to somebody else’s system, would be a criminal offence. The only thing separating security work from an intrusion is written authorisation and agreed scope. Professionals treat this as paperwork that protects them, because it does. Read this section before your first command and ask about anything ambiguous rather than assuming.

In scope
The secure_robotstore sandbox. Your own local docker compose stack. The lab robot, only under the hardware protocol below. Test accounts you were issued.
Out of scope
Any production or school deployment. Any robot other than the designated lab unit. Campus network infrastructure — switches, access points, the university’s own services. Any third‑party service, including AWS control‑plane APIs beyond our own account. Other people’s laptops and accounts.
Never permitted
Denial‑of‑service testing against shared infrastructure. Social engineering of staff, students or suppliers. Physical tampering with devices that are not the lab unit. Copying real video or personal data onto a personal machine. Publishing a finding outside the team before it is fixed.
Hardware protocol
Simulation first. Then the robot on blocks, wheels clear of the ground. Only then the floor — in a cleared area, with a second person holding a physical emergency stop and no one else within three metres. A test that would be unsafe if it worked is not run.
If you find something real
Stop. Do not explore further, do not pivot, do not test how far it goes. Write down exactly what you did, capture the evidence you already have, and tell your supervisor the same day. In particular: if you discover you can reach something outside the scope above, that is the moment to stop, not the moment to confirm it.
Reporting format
One page per finding: what it is, the exact steps to reproduce, the impact in plain language, the severity you propose and why, and a suggested fix. Use docs/security-findings.md as the model — it traces every finding to a file and line and records how it was found.

The line you do not cross

“I was only testing” is not a defence, and curiosity is not authorisation. If a step is not clearly inside the scope above, it is outside it until someone tells you otherwise in writing. Asking costs you an hour; guessing wrong can end an internship and, on a system attached to machinery near children, cause real harm.

Foundation

T01

Map the attack surface

Both2 daysNo code changes
Objective

Produce a complete, evidence-based inventory of everything this system exposes — every listening port, every HTTP route, every MQTT topic, every credential — before forming any opinion about whether it is secure.

Why it matters

You cannot defend what you have not enumerated, and almost every real breach begins with something nobody knew was listening. Finding F1 in our own audit was exactly this: a health endpoint on 0.0.0.0 that everyone had forgotten was published. An inventory built by reading code and probing a running system finds those; an inventory built from the architecture diagram never does.

Steps
  1. Start the sandbox: cd secure_robotstore && make up. Confirm it is healthy.
  2. Enumerate listening sockets on the host and note which bind 0.0.0.0 versus 127.0.0.1. Explain, for each, who can reach it from where.
  3. Enumerate HTTP routes from the live OpenAPI document at localhost:8001/docs, then cross-check against the source — note anything reachable that is not documented.
  4. Enumerate MQTT topics by subscribing to # and watching for sixty seconds. Compare what you observe against the topic modules in the source.
  5. Find every credential in the repository: passwords, tokens, keys, defaults. Record where each is defined and where it is consumed.
  6. Repeat steps 2–4 against the main stack (docker compose up at the repository root) and note every difference.
Done when
  • A single Markdown table lists every port, route and topic with its authentication status and its binding interface.
  • Every entry cites the file and line that creates it — no entry is there because you assumed it.
  • You can name, without looking, which three exposures you would fix first and why.
Verify
# every listening socket, and what is behind it
ss -tlnp | sort -k4
docker compose ps --format '{{.Name}}\t{{.Ports}}'

# every route the API actually serves
curl -s localhost:8001/openapi.json | python3 -c \
  'import sys,json;[print(m.upper(),p) for p,o in json.load(sys.stdin)["paths"].items() for m in o]'

# every topic in use, live
docker run --rm --network secure-robotstore_secure-robotstore-net eclipse-mosquitto:2 \
  mosquitto_sub -h mosquitto -t '#' -v
Deliverable docs/attack-surface.md Reference docs/security-findings.md §F1
T02

Prove three vulnerabilities and write them up

Both2 daysTH-01
Objective

Demonstrate, against the running sandbox, that an unauthenticated attacker can forge robot data, read all traffic, and call the API — then write each one up to the standard our own audit uses.

Why it matters

Writing a finding well is a distinct skill from finding it, and it is the one that determines whether anything gets fixed. A report that says “MQTT is insecure” is ignored. A report that shows a forged row landing in the system of record, names the file and line that allowed it, and states the impact in terms a non-engineer understands, gets prioritised the same week.

Steps
  1. Run make verify-holes and read what it does — it is three commands, not a magic script.
  2. Reproduce each by hand so you understand every flag. Capture the output.
  3. For the forged reading, follow it all the way through: confirm it in Redis, in Postgres, and arriving in an open browser window. That whole path is the impact.
  4. Trace each vulnerability to the specific line that permits it, and to the design decision behind that line.
  5. Write three findings: summary, severity with justification, reproduction steps, affected file and line, impact, suggested fix, and how to verify the fix.
  6. Rate each one yourself before looking at how we rated it, then compare and account for the difference.
Done when
  • Three findings written, each reproducible by someone else using only your steps.
  • Each cites a file and line, not a component name.
  • Impact is stated in terms of what happens to a school, not what happens to a process.
Verify
# 1 — forge a reading with no credentials at all
docker run --rm --network secure-robotstore_secure-robotstore-net eclipse-mosquitto:2 \
  mosquitto_pub -h mosquitto -t devices/demo-device-01/int -m '{"value":999,"seq":999999}'

# it is now permanently in the system of record
docker exec sr-postgres psql -U robotstore -d robotstore \
  -c "SELECT * FROM int_readings WHERE seq = 999999;"

# 3 — the API needs no token
curl -s -o /dev/null -w "%{http_code}\n" localhost:8001/api/string/history
Deliverable three findings in docs/findings/ Reference docs/security-findings.md
T03

Build the threat model yourself

Both3 daysDesign
Objective

Draw the system’s data flows, mark the trust boundaries, and apply STRIDE at each boundary to produce your own threat register — independently, before reading section 08 of this document again.

Why it matters

A threat model you were handed is a document. A threat model you built is a way of thinking, and it transfers to every system you work on afterwards. This is also the task where you will discover threats this document missed — two fresh readers with no assumptions routinely find things the people who built a system cannot see any more.

Steps
  1. Draw the data flow diagram from the code, not from the architecture docs. Every process, every data store, every flow between them.
  2. Mark every place where data crosses from one trust level to another. Justify each boundary in one sentence.
  3. At each boundary, work through all six STRIDE categories and write at least one concrete threat for each that applies — concrete meaning it names a topic, route or file.
  4. Rate each threat by impact and likelihood. Impact is harm to people and schools, not technical severity.
  5. Now compare with section 08. For every difference, decide which of you is right and write down why.
  6. Bring the differences to your supervisor. The ones where you are right go into the real register.
Done when
  • A data flow diagram with boundaries, generated from reading source.
  • At least twenty concrete threats, each naming a specific file, route or topic.
  • A written reconciliation against section 08, including at least one threat this document does not contain.
Verify

Peer review: your track partner must be able to take your diagram alone and independently arrive at three of your threats without being told them. If they cannot, the diagram is not yet showing the mechanism.

T04

Give every MQTT client its own identity

Track A3 daysB3TH-01
Objective

Turn off anonymous access at the broker and give the agent and the backend separate credentials, sourced from the environment and never committed.

Why it matters

This is the single largest hole in the sandbox and the foundation every later control rests on. Authorisation is meaningless without identity: an ACL cannot scope a client to its own topics if the broker does not know which client it is. Right now anyone who can reach port 1883 is implicitly the most trusted party in the system.

Steps
  1. Set allow_anonymous false and add a password_file to the broker config.
  2. Generate the password file at container start from environment variables, so no plaintext ever enters git. Read docker-entrypoint-wrapper.sh in the main stack for the pattern — it exists for exactly this reason.
  3. Create two identities with different passwords: one for the agent, one for the backend.
  4. Call username_pw_set() before connect_async() in both clients. The INTERN TASK comments mark the exact place.
  5. Plumb the credentials through compose and the settings modules. No defaults that work.
  6. Restart and confirm both legitimate clients reconnect — then confirm an anonymous one cannot.
Done when
  • Anonymous publish and subscribe are both refused by the broker.
  • Agent and backend hold distinct credentials and both still work.
  • No password appears anywhere in git history or in a committed file.
  • A wrong credential produces a clear log line, not silence.
Verify
# must now FAIL
docker run --rm --network secure-robotstore_secure-robotstore-net eclipse-mosquitto:2 \
  mosquitto_pub -h mosquitto -t devices/demo-device-01/int -m '{"value":1,"seq":1}'

# must still be true — the real clients are unaffected
curl -s localhost:8001/health/detail | python3 -m json.tool   # mqtt.connected: true
curl -s localhost:8081                                        # mqtt_connected: true
Watch for paho retries forever in the background — a wrong password looks like silence, not an error. Read the broker log. Reference cloud-container/mosquitto/
T05

Enforce direction with a topic ACL

Track A3 daysB3TH-01
Objective

Restrict each identity to the topics its role legitimately needs, in the direction it legitimately needs them — the device writes telemetry and reads commands; the backend writes commands and reads telemetry.

Why it matters

Authentication proves who a client is; it does nothing about what they may then do. Without an ACL, a compromised backend can fabricate a robot’s self-reported state, and anything holding the device credential can publish commands to every other device. This is the control that contains a breach to one machine instead of the fleet — see section 03.

Steps
  1. Write an acl_file granting the backend read on telemetry topics and write on the command topic — and explicitly not write on telemetry.
  2. Use a pattern rule with %u so each device is scoped to its own namespace automatically. Understand why this means adding a device never edits the ACL file.
  3. Reload the broker and confirm normal operation is untouched.
  4. Attempt each of the four forbidden combinations and confirm all four are refused.
  5. Write down what an attacker holding the device credential can still do. That residual is the input to T14.
Done when
  • The backend identity cannot publish telemetry, status or health.
  • The device identity cannot publish to the command topic.
  • Neither identity can subscribe to a topic outside its role.
  • Real telemetry and real commands both still flow.
Verify
# backend identity forging device telemetry — must be refused
mosquitto_pub -h localhost -p 1884 -u backend -P "$MQTT_BACKEND_PASSWORD" \
  -t devices/demo-device-01/string -m '{"value":"forged","seq":1}'

# device identity issuing a command — must be refused
mosquitto_pub -h localhost -p 1884 -u demo-device-01 -P "$MQTT_DEVICE_PASSWORD" \
  -t devices/demo-device-01/cmd -m '{"action":"drive"}'
Deliverable ACL file + a table of what each role may do Reference cloud-container/mosquitto/aclfile
T06

Bound every input that crosses the wire

Track A3 daysB2 · B3TH-06 TH-10
Objective

Cap payload size at the broker, at the backend before parsing, and at the value level in the store — three layers, because each catches what the others cannot.

Why it matters

The backend parses every inbound message with json.loads on the single asyncio event loop that serves every WebSocket client in the system. One oversized payload from one client stalls telemetry for every school at once. This was finding F2, rated high, and the fix is four lines of config plus a length check — a good demonstration that severity and effort are unrelated.

Steps
  1. Measure the largest legitimate message your system sends. Derive the limit from that, with headroom — do not pick a round number.
  2. Set message_size_limit, max_connections, max_queued_messages, max_inflight_messages and max_keepalive at the broker. Write a comment explaining each number.
  3. Add a byte-length check in the MQTT service before json.loads, not after.
  4. Add a value-length cap in the store for payloads that are small enough to parse but still unreasonable.
  5. Test the boundary exactly: one byte under, exactly at, one byte over.
Done when
  • An oversized publish is dropped and never reaches Postgres.
  • Normal readings continue flowing throughout the attack.
  • A test covers the exact boundary, and another asserts the ceiling itself stays sane.
Verify
# attach a subscriber first — mosquitto_pub exits 0 even when the broker drops the message,
# so exit codes prove nothing here. Delivery is the only honest test.
python3 -c "print('{\"value\":\"' + 'A'*5000000 + '\",\"seq\":424242}')" > /tmp/huge.json
mosquitto_pub -h localhost -p 1884 -t devices/demo-device-01/string -f /tmp/huge.json

docker exec sr-postgres psql -U robotstore -d robotstore \
  -c "SELECT count(*) FROM string_readings WHERE seq = 424242;"   # must be 0
curl -s localhost:8001/health/detail   # backend still healthy
Watch for exit codes lie here. Verify by delivery, with a subscriber attached. Reference docs/security-findings.md §F2, §F4
T07

Encrypt the device link

Track A4 daysB3TH-03
Objective

Move MQTT onto a TLS listener on 8883 with certificate verification on both clients, and keep it working after a restart.

Why it matters

T04 gave every client a password. Without TLS, that password crosses campus Wi‑Fi in plaintext on every connect — so anyone running a packet capture in the same building now has it, and T04’s work is undone. Encryption and authentication are not alternatives; one without the other is a false sense of security.

Steps
  1. Generate a development CA and server certificate. Read scripts/generate-dev-certs.sh rather than inventing the process.
  2. Add a TLS listener on 8883 with the CA and certificate configured.
  3. Call tls_set() on both paho clients before connect_async(), and make the CA path configurable.
  4. Make the port and TLS mode configuration, not code — enabling TLS in production must not require a code change.
  5. Prove encryption by capturing traffic on both ports and comparing.
  6. Then deliberately break it: point a client at a certificate that does not match and confirm it refuses rather than silently downgrades.
Done when
  • Both clients connect over 8883 and the plaintext listener is closed or restricted.
  • A packet capture on the TLS port shows no readable topic names or payloads.
  • An untrusted certificate is rejected, with a log line saying so.
Verify
# plaintext: readable. TLS: not.
sudo tcpdump -i any -A -c 40 'port 1884' | grep -c 'devices/'
sudo tcpdump -i any -A -c 40 'port 8883' | grep -c 'devices/'    # expect 0

# a client with no CA must be refused, not downgraded
mosquitto_sub -h localhost -p 8883 -t 'devices/#' -v
Watch for paho applies TLS when the socket is created — tls_set() after connect_async() silently does nothing and you get a plaintext connection that looks fine. Reference scripts/generate-dev-certs.sh, §F6
T09

Store and check credentials properly

Track B3 daysB1TH-08
Objective

Replace the plaintext credential dictionary with hashed storage, a constant-time comparison, and one generic failure message for every kind of failure.

Why it matters

The current login tells an attacker whether a username exists before they try a single password — free user enumeration. It then compares the password with ==, which returns faster the earlier it finds a mismatch, leaking the same information through timing even after you fix the message. Both are small code changes and both are the difference between a login that resists an attacker and one that helps them.

Steps
  1. Reproduce the enumeration: two requests, two different responses. Capture it.

Make a command provable, not merely delivered

Track A5 daysB3TH-04Flagship
Objective

Wrap every command in a signed envelope carrying the authorising operator, a unique nonce, an issue time and a short expiry — and make the robot reject anything replayed, stale or unsigned.

Why it matters

This is the task that separates robotics security from web security, and it is the one to do properly. Your ACL work in T05 stops the wrong client from publishing. It does nothing about a command that was legitimate once: capture a “drive forward” message today, publish it again tomorrow, and the robot obeys — the bytes are genuine, the topic is right, the publisher is authorised. Nor does the ACL tell the robot which human authorised motion, which is what an audit trail needs to mean anything. “This arrived over an authenticated channel” is not “a specific person asked for this, just now.”

Steps
  1. Demonstrate the replay first. Subscribe, capture a real command, wait, publish it back verbatim, and watch the robot act on it. Record that.

  4. Reject on a bounded freshness window — a command older than a small number of seconds is refused regardless of signature.
  5. Keep a bounded nonce cache on the robot so a replay inside the freshness window is still refused. Bound it, and say what happens when it is full.
  6. Handle clock skew deliberately. A robot with a wrong clock rejecting every command is a self-inflicted outage; write down how you detect and handle it.
  7. Count and expose rejections by reason, so an attack in progress is visible rather than silent.
Done when
  • A captured command replayed after the window is rejected.
  • A captured command replayed inside the window is rejected by nonce.
  • An unsigned or tampered command is rejected before reaching actuator code.
  • Every rejection is counted by reason and visible in metrics.
  • Normal teleoperation is unaffected, and you have measured the added latency.

Make the record tamper-evident

  3. Triage: for each high or critical finding, decide whether it is reachable in our usage. Not every vulnerability in a shipped library is exploitable in your code, and saying so with reasons is the skill.
  4. Pin what is not pinned. An unpinned dependency means your build is not reproducible and a compromised release lands silently.
  5. Add the scan to continuous integration with a threshold that fails the build, and a documented exception process for accepted findings.
  6. Write the update policy: who checks, how often, and how an emergency patch reaches a fleet of robots at the edge.
Done when
  • A bill of materials exists for every image and is regenerated by the build.
  • Scans run in CI and fail the build above an agreed threshold.
  • Every current high or critical finding is triaged with a written decision.
  • The update and emergency-patch policy is documented.

Monday

Plan and predict

Midweek

Swap and review

Read your partner’s open pull request properly — not for style, but for the question “what does this still not stop?”. That question is the whole job.

Demo the proof, not the code

Fifteen minutes: run the attack against the old build so it works, run it against the new one so it fails, run the app so it still works. Three commands, live.

Capstone — the tabletop, week 12

Two hours, no keyboards. Your supervisor presents a scenario: a teacher reports that a robot moved on its own during a lesson, and the operator who appears in the logs says it was not them. Working from the audit trail and the detection you built, you two must answer: what happened, which control failed, how would we know if it happened again, and what do we tell the school today? This is the exercise that ties every task together — and it is the closest thing to real incident response you can run without a real incident.

What you should be able to do at the end

Take an unfamiliar system, enumerate what it exposes, model how it could be attacked, implement controls at the right layer, prove they work, and explain honestly what they still do not cover. That transfers to every system either of you will work on afterwards — the MQTT specifics are the vehicle, not the destination.

Glossary

Terms used above that a second-year computer science course may not have covered yet. Ask about anything still unclear — nobody is expected to arrive knowing these.

MQTT
A lightweight publish/subscribe messaging protocol built for devices on unreliable networks. Clients publish to a topic; the broker delivers to everyone subscribed to it. Nobody addresses anybody directly.
Broker
The server in the middle of MQTT. Every message passes through it, which is why it is the natural place to enforce who may say what.
ACL
Access control list. Here, the broker file stating which authenticated identity may publish or subscribe to which topic patterns.
QoS 0/1/2
MQTT delivery guarantees: fire-and-forget, at-least-once, exactly-once. Telemetry at 1 Hz uses 0 — a redelivered stale reading is worse than a missing one. A command channel wants 1.
Trust boundary
A point where data moves between components with different trust levels. The receiving side must independently decide whether to act, rather than trusting the fact of arrival.
STRIDE
A checklist for finding threats: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege. Applied at each boundary so nothing is missed by accident.
JWT
JSON Web Token. A signed, self-describing token the server can verify without a database lookup. Its strength is statelessness; its weakness is that it cannot be cancelled before expiry without extra machinery.
jti
A unique identifier inside a JWT. The handle a revocation list keys on, which is how a stateless token becomes cancellable at logout.
mTLS
Mutual TLS. Both sides present certificates, so the server proves its identity to the client and the client proves its identity to the server. This is how per-device identity is normally done.
Replay attack
Capturing a legitimate message and sending it again later. The bytes are genuine and the signature valid, so only a nonce or an expiry can distinguish it from the original.
Nonce
A number used once. Recorded by the receiver so the same message cannot be accepted twice.
Constant-time compare
Comparing secrets in a way that takes the same time regardless of where they differ. A normal comparison returns early on the first mismatch, leaking how much of a guess was correct through timing.
Watchdog
A timer that triggers a safe action when something expected stops arriving. Here: no fresh command within an interval means command zero velocity.
cmd_vel
The ROS2 topic carrying velocity commands to a robot base. The last software step before motors turn — and therefore the last place anything can be stopped.
SDP / ICE / TURN
WebRTC machinery. SDP describes a media session, ICE finds a network path between two peers, and TURN relays media when no direct path exists. SDP is attacker-influenced text that reaches C libraries, which is why it is size- and format-checked.
Row-level security
A PostgreSQL feature applying a filter to every query automatically. Makes a forgotten tenant filter return nothing instead of everything.
SBOM
Software bill of materials: the full list of third-party components in a build, so a new advisory can be matched against what you actually ship.
Least privilege
Every identity gets exactly the access it needs and nothing more, so a compromise of any one of them is bounded.
